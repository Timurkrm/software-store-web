# Материалы к пояснительной записке

## Введение

Проект «Разработка веб-приложения по продаже программного обеспечения» реализует учебный интернет-магазин ПО. Цель работы — применить web-стек Java для полного пользовательского цикла: от поиска продукта до оформления заказа, demo-оплаты и выдачи лицензии. Решение развёртывается как WAR или через Docker Compose и использует PostgreSQL.

# 1. Анализ предметной области

## 1.1 Назначение системы

SoftStore ведёт каталог программных продуктов и даёт зарегистрированному пользователю серверную корзину. После оформления заказа фиксируется состав покупки и цена каждой позиции. Успешная demo-оплата создаёт запись платежа и лицензии. Администратор управляет категориями и товарами, архивирует товары и просматривает заказы.

## 1.2 Пользователи

- **Посетитель** просматривает каталог, ищет продукт, открывает карточку, регистрируется или входит.
- **USER** дополнительно управляет собственной корзиной, видит только свои заказы и лицензии, оплачивает собственный ожидающий оплаты заказ.
- **ADMIN** дополнительно управляет продуктами и категориями, получает список заказов и может выполнить только допустимый статусный переход.

## 1.3 Основные бизнес-процессы

1. Посетитель получает публичный список активных продуктов и категорий.
2. Пользователь проходит регистрацию и получает JWT при входе.
3. Пользователь добавляет активный продукт в серверную корзину, корректирует количество и создаёт заказ.
4. `CheckoutFacade` фиксирует `OrderItem.unitPrice`, рассчитывает сумму и создаёт заказ `PENDING_PAYMENT` из корзины.
5. Оплата переводит заказ через `PAID` в `COMPLETED`, создаёт платёж и лицензии на позиции заказа.
6. Администратор создаёт/изменяет категории и продукты, архивирует продукты и отменяет только созданные или ожидающие оплаты заказы.

Последовательности API отражены в [api-sequence.puml](../05-design/api-sequence.puml).

## 1.4 Анализ требований

Решение реализует web-интерфейс на Thymeleaf, REST API `/api/v1`, JWT-аутентификацию, роли USER/ADMIN, PostgreSQL/Flyway, Docker и WAR. Нереализованными намеренно остаются внешняя платёжная интеграция, возвраты, refresh tokens и сложная pagination: оплата является учебным demo-процессом.

# 2. Проектирование

## 2.1 Архитектура PCMEF

Зависимости организованы в направлении:

```text
Presentation → Control → Mediator → Entity → Foundation
```

- **Presentation**: MVC/REST-контроллеры, Thymeleaf pages, DTO и обработчик ошибок.
- **Control**: интерфейсы бизнес-сервисов (`IUserService`, `IProductService`, `IOrderService` и др.).
- **Mediator**: реализации сценариев (`UserMediator`, `CartMediator`, `CheckoutFacade`, `PaymentMediator`, `LicenseMediator`).
- **Entity**: JPA-сущности предметной области.
- **Foundation**: Spring Data JPA repositories и bootstrap demo-данных.

Контроллеры не обращаются к repositories напрямую. `CheckoutFacade` является естественным Facade: он координирует создание заказа, обработку платежа и выдачу лицензий. Обзор ключевых зависимостей приведён в [design-class-diagram.puml](design-class-diagram.puml).

## 2.2 Компоненты системы

Spring MVC обслуживает HTML и JSON API. JavaScript-клиент использует `Fetch API`, хранит JWT и небольшие сведения о пользователе в `localStorage`, а корзина всегда остаётся на сервере. Spring Security работает stateless; `JwtAuthFilter` устанавливает аутентификацию только при наличии Bearer token. OpenAPI описывает API в Swagger UI.

## 2.3 Модель данных

Модель включает `User`, `Category`, `SoftwareProduct`, `Cart`, `CartItem`, `Order`, `OrderItem`, `Payment`, `License`. Категория нормализована, продукт ссылается на неё; у пользователя одна корзина. Заказ содержит позиции с историческим `unitPrice`, поэтому изменение цены товара не меняет прошлые заказы. Продукты архивируются вместо удаления. Полная схема и ограничения приведены в [ER-диаграмме](../04-database/er-diagram.puml) и [описании БД](../04-database/README.md).

## 2.4 REST API

API использует JSON и префикс `/api/v1`. Публичны регистрация/вход и GET каталога/категорий. JWT требуется для корзины, заказов и лицензий; admin API требует `ROLE_ADMIN`. DTO проходят Bean Validation, а ошибки возвращаются моделью `ApiError` со статусами 400, 401, 403, 404 и 409. Полный перечень endpoints дан в [rest-api.md](../05-design/rest-api.md); интерактивная документация доступна по `/swagger-ui/index.html`.

## 2.5 Безопасность

Пароли хешируются BCrypt. JWT передаётся в `Authorization: Bearer <token>`. `RestAuthenticationEntryPoint` и `RestAccessDeniedHandler` возвращают JSON вместо HTML-страниц Spring Security. Параметризованные JPA/Spring Data запросы защищают от SQL-инъекций; пользовательские значения в UI добавляются через `textContent`, а не через `innerHTML`. Статические ресурсы и публичные GET endpoint'ы не требуют токена.

## 2.6 UI

Есть девять web-страниц: главная, аутентификация, каталог, продукт, корзина, профиль, заказы, лицензии и admin. Адаптивный CSS переводит сетки и формы в одну колонку на малых экранах. Подробности взаимодействия приведены в [руководстве пользователя](../12-user-guide/README.md) и [описании UI](../07-ui/README.md).

# 3. Реализация

## 3.1 Backend

Проект построен на Java 17 и Spring Boot 3. Maven управляет зависимостями и сборкой. Приложение создаёт executable WAR и может запускаться через `mvn spring-boot:run`, `java -jar` или Docker.

## 3.2 Entity и Foundation

JPA/Hibernate реализуют Data Mapper через сущности и Spring Data repositories. Hibernate Persistence Context выполняет функцию Identity Map. Связи используют LAZY-загрузку; методы истории заказа применяют `@Transactional(readOnly = true)` и точечный `@EntityGraph` для `items` и `items.product`, чтобы DTO маппились без `LazyInitializationException`.

## 3.3 Mediator и Control

Control-интерфейсы отделяют Presentation от реализаций. `ProductMediator` обслуживает публичный каталог и архивирование; `CategoryMediator` проверяет уникальность имени и запрещает удаление используемой категории; `CartMediator` рассчитывает серверную корзину. `CheckoutFacade` формирует заказ из корзины, а `PaymentMediator` и `LicenseMediator` завершают payment/license flow.

## 3.4 Presentation и JWT

REST-контроллеры возвращают DTO, не JPA-сущности. `AuthController` создаёт пользователя и возвращает JWT при успешном логине. Страницы Thymeleaf являются UI shell, а защищённые данные получают через API. API-клиент добавляет заголовок Bearer только при наличии token и перенаправляет на вход при реальном 401 защищённого запроса.

## 3.5 Корзина, заказ, оплата и лицензии

Для корзины доступны добавление, изменение количества, удаление и очистка. Создание заказа из пустой корзины запрещено. Цена фиксируется в `OrderItem`, доступ к чужим заказам исключён поиском по идентификатору пользователя. Оплатить можно только `PENDING_PAYMENT`; выдача лицензий следует за успешной demo-оплатой. Повторная оплата завершённого заказа отклоняется статусным правилом.

## 3.6 Администрирование

Администратор получает CRUD категорий и продуктов; удаление продукта является архивированием. Физическое удаление категории запрещено, если есть связанные продукты. Admin orders позволяют просмотр и отмену допустимых заказов; выставление `PAID` или `COMPLETED` вручную не допускается. Подробный порядок действий дан в [руководстве администратора](../13-admin-guide/README.md).

# 4. Тестирование

## 4.1 Unit tests

Mockito unit tests покрывают UserMediator, ProductMediator, CategoryMediator, CartMediator, CheckoutFacade, PaymentMediator и LicenseMediator. Проверяются регистрация, дубликаты, изменение/архивирование продукта, конфликты категории, операции корзины, создание заказа, оплата и выдача лицензий.

## 4.2 MockMvc

Интеграционные MockMvc-проверки подтверждают публичный каталог, 401 для корзины без JWT, 403 для USER на admin endpoint, JSON-ошибки и validation 400.

## 4.3 JaCoCo и Checkstyle

После `mvn clean test`: 42 теста, 0 failures, 0 errors; JaCoCo instruction coverage — 61.51%, line coverage — 62.69%. `mvn checkstyle:check` сообщает 0 violations. Детали — в [docs/08-testing](../08-testing/README.md) и [docs/09-refactoring](../09-refactoring/README.md).

## 4.4 Исправленные ошибки

Исправлены JSON-обработчики 401/403, порядок public matchers и поведение JWT filter без Bearer header. Дополнительно исправлена загрузка истории заказов: EntityGraph и read-only транзакции исключили `LazyInitializationException` при чтении `Order.items` и `OrderItem.product`.

# 5. Развёртывание

## 5.1 Maven WAR и Tomcat

`mvn clean package` создаёт `target/software-store.war`. `SoftwareStoreApplication` расширяет `SpringBootServletInitializer`, поэтому WAR совместим с Tomcat 10+ и одновременно запускается как executable archive.

## 5.2 Docker и PostgreSQL

`docker compose up -d --build` создаёт `app` и PostgreSQL 16. Для БД используется healthcheck `pg_isready`, и app зависит от healthy DB. В проверенном окружении Flyway успешно валидировал две миграции, а public pages/API и Swagger возвращали 200.

## 5.3 Environment variables

Подключение к БД, JWT secret и seed-admin передаются через environment variables. `.env.example` содержит только placeholders и не хранит настоящих секретов. Профиль `dev` включает идемпотентные demo-данные; production-like запуск использует другой профиль. Инструкции: [docs/10-deployment](../10-deployment/README.md).

# 6. Управление проектом

WBS, учебный Gantt и Basic COCOMO зафиксированы в [docs/11-project-management](../11-project-management/README.md). Оценка выполнена для 1.451 KLOC Java-кода: 3.55 чел.-месяца, 4.05 месяца и средняя команда 0.88 человека. Это учебная модельная оценка.

## Заключение

Реализованное приложение покрывает ключевой сценарий продажи ПО: публичный каталог, JWT-аутентификация, серверная корзина, создание заказа, demo-оплата, выдача лицензий и административное управление каталогом. Проверенная сборка формирует WAR, Docker Compose поднимает приложение с PostgreSQL, а тесты и статический анализ проходят без ошибок.
